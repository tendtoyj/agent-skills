# Estimate Task

Research 문서를 기반으로 작업의 규모, 복잡도, 리스크를 분석하고 작업 분할 방안을 논의하는 세션을 진행한다.

## Step 1: 문서 선택

인자로 문서 번호가 주어진 경우 `thoughts/research/` 에서 해당 번호로 시작하는 파일을 찾아 읽는다.

인자가 없는 경우:
1. `thoughts/research/` 디렉토리의 .md 파일 목록을 조회한다 (`done/` 하위 제외)
2. AskUserQuestion으로 어떤 리서치 문서를 바탕으로 논의할지 선택을 받는다

선택된 문서를 전체 읽는다.

## Step 2: 범위 및 규모 분석

리서치 문서 내용을 바탕으로 다음을 분석하여 표 형태로 정리한다.

### 2-A. 작업 범위 (Scope)

수정 대상 파일/모듈을 나열하고 각각에 대해:
- **파일 경로**: 수정이 필요한 파일
- **변경 유형**: 신규 생성 / 수정 / 삭제
- **변경 규모**: 소(몇 줄) / 중(함수 단위) / 대(모듈 전체)
- **변경 내용 요약**: 어떤 변경이 필요한지 한 줄 설명

| 파일 | 변경 유형 | 규모 | 요약 |
|------|----------|------|------|
| `path/to/file` | 수정 | 중 | 설명 |

하단에 총 파일 수, 신규/수정/삭제 비율을 요약한다.

### 2-B. 영향 분석 (Impact & Risk)

다음 관점에서 영향을 분석한다:

**기능 영향**:
- 직접 영향받는 기능 목록
- 간접 영향이 우려되는 기능 목록

**리스크 고려사항**:
- 회귀(regression) 가능성이 있는 영역
- 기존 동작이 변경되는 부분
- 마이그레이션이 필요한 부분
- 성능에 영향을 줄 수 있는 부분

**리스크 등급**:
- 🟢 `낮음` — 기존 동작에 영향 없음, 독립적 변경
- 🟡 `보통` — 간접 영향 가능, 주의 필요
- 🔴 `높음` — 핵심 경로 변경, 회귀 가능성 있음

## Step 3: 작업 분할 논의

분석 결과를 바탕으로 작업을 어떻게 나눌지 제안한다.

### 판단 기준

다음 조건 중 하나라도 해당하면 **분할 작업**으로 권장:
- 수정 파일이 5개 이상
- 서로 다른 레이어(예: backend + frontend)를 동시에 건드림
- 리스크 🔴 항목이 1개 이상
- 독립적으로 검증 가능한 단위가 2개 이상

### 제안 형식

**한 번에 완료 가능한 경우:**
```
✅ 단일 작업으로 진행 가능
- 예상 규모: [소/중/대]
- 이유: [판단 근거]
```

**분할이 필요한 경우:**
```
📋 N개 작업으로 분할 권장

작업 1: [제목]
- 범위: [파일 목록]
- 목표: [이 작업이 완료되면 무엇이 달라지는지]
- 선행 조건: 없음 / 작업 N

작업 2: [제목]
- 범위: [파일 목록]
- 목표: [이 작업이 완료되면 무엇이 달라지는지]
- 선행 조건: 작업 1
```

분할 시 각 작업의 의존 관계와 순서도 명시한다.

## Step 4: 논의

Step 2, 3의 결과를 대화에 출력한 뒤 사용자에게 질문한다:
- 분석 내용 중 동의하지 않는 부분이 있는지
- 추가로 고려해야 할 사항이 있는지
- 작업 분할 방식에 대한 의견

사용자와 합의가 될 때까지 반복한다.

## Step 5: 결과 저장

논의가 완료되면 AskUserQuestion으로 "estimation 문서로 저장할까요?" 확인 후, 동의 시:

1. `thoughts/estimation/` 디렉토리가 없으면 생성
2. 기존 파일의 번호를 확인하여 다음 순번을 결정 (3자리, 001부터)
3. 아래 형식으로 저장:

```markdown
---
date: [ISO 날짜]
source_research: "[리서치 문서 파일명]"
status: estimated
---

# Estimation: [주제]

## 원본 리서치
- 문서: `thoughts/research/NNN_topic.md`

## 범위 분석
[Step 2-A 내용]

## 영향 및 리스크 분석
[Step 2-B 내용]

## 작업 분할
[Step 3 내용]

## 논의 사항
[Step 4에서 합의된 추가 사항이 있으면 기록]

## 다음 단계
- [ ] `create-plan` 으로 구현 계획 수립
```

파일명: `thoughts/estimation/NNN_{주제_요약}.md`

## Guidelines

- 코드베이스를 직접 탐색하지 않는다. 리서치 문서의 내용만으로 판단한다.
- 주관적 판단이 포함되므로 항상 근거를 함께 제시하여 사용자가 동의/반박할 수 있게 한다.
- 리서치 문서에 정보가 부족하면 "리서치 보완 필요" 항목으로 명시한다.
- 이 세션의 목적은 계획 수립이 아니라 **규모 파악과 작업 분할 합의**이다. 구체적인 구현 방법은 `create-plan`에서 다룬다.
